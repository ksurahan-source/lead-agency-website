# 좋은 부분을 보존하며 수정

수정의 단위는 ‘더 멋있게’가 아니라 **관찰한 결함 하나와 보존할 선택**이다. 고객이 유지하라고 한 얼굴·제품·구도·대사·길이를 먼저 고정한다. 같은 요청을 이유 없이 전체 재생성하지 않는다.

1. 실제 파일/이미지/검수본과 고객 의견을 확인한다. 이미지가 없으면 관찰했다고 쓰지 않고 고객이 설명한 증상에 대한 가설로 제시한다. 영상은 프레임만 봤다면 동작·음향을 확인했다고 쓰지 않는다.
2. 관찰 → 원인 가설 → 최소 수정 → 보존 → 재검수 기준의 5칸을 작성한다. [결함 진단 예시](references/diagnose.md)는 질감/환상/리듬/정체성 문제에 필요할 때 읽는다.
3. 영향을 받는 장면 ID와 원본 버전을 지정한다. 어떤 카드를 바꾸면 공유 장면에 영향이 생기는지 확인한다. 한 장면의 조명 결함을 공용 인물 카드의 얼굴 변경으로 고치지 않는다.
4. 지금 도구에서 가능한 수정을 선택한다. 이미지 편집·다중 참조·마스크 입력을 실제 도구가 제공할 때만 사용한다. 참조 강도/seed/overlay 같은 필드를 발명하지 않는다. 재생성 비용과 요청 ID는 현재 승인 범위와 기존 진행 상태를 따른다.
5. 결과를 원본과 같은 비교 조건으로 본다. 목표 결함이 줄었는지와 보존 조건이 유지됐는지를 함께 판단한다. 개선 없는 반복은 원인 가설을 바꾸거나 고객에게 결정할 자료를 제시한다. 최대 시도 횟수는 승인된 예산/시간 범위에서 정하며 무한 재생성하지 않는다.

구조화된 수정 요청이 있으면 `creative_board_check`로 참조/범위를 검사한다. 이 검사는 미적 개선을 측정하지 않는다. 실제 HIOB 영상 리뷰는 원본 해시·검수 범위가 확인된 상태에서 `feedback_save`/`material_review`/최종 review 도구의 현재 스키마로 남긴다. 아직 생성하지 않은 이미지 기획서에 영상 검사 ID나 SHA를 만들지 않는다.

마지막 전달은 바뀐 이미지/장면, 유지한 부분, 확인한 범위, 남은 결함, 다음 결정이다. 모델의 자기 평점만으로 고객 만족이나 광고 성과를 인증하지 않는다.

## 여러 자료의 검사와 대기

검사는 워크스페이스 전체에서 미완료 10,000개, UTC 하루 신규 접수 10,000개·재시도 포함 실행 10,000회를 공유한다. 전체 서버는 실제 4개씩 병렬 처리하며 나머지는 큐에서 기다린다. 일일 한도는 UTC 00:00(한국 09:00)에 초기화된다. pending은 실패가 아니다. 오디오는 반환된 jobId로 audio_inspection_status를 조회하고 영상·최종본은 같은 검사 도구와 인자를 약 60초 간격으로 다시 호출한다. requestId·jobId·원본 해시·검사 설정을 보존하며 대기 중 새 생성이나 렌더를 요청하지 않는다. 한도 오류와 실행 순서는 MCP 리소스 `hiob://inspection-guide`를 읽는다. 완료 결과의 재사용도 현재 프로젝트 권한·원본·설정 일치를 확인한다. 검사 수치만으로 창작 품질을 합격 처리하지 않는다.
